# 실시간 3D 영웅 시험 (순신) — 구운 스프라이트와 비교

시험 브랜치 `claude/live3d-spike-76e52e`. 합치지 않는다 (사용자 결정 전). 기본값은 지금 방식 그대로라 다른 작업에 영향 없음.

## 한 줄 결론

동작은 확실히 좋아진다 (60fps·섞기·자유 방향·달리며 공격). 영웅 한 명은 PC에서 GPU 0.35ms로 가볍다.
적 떼(30마리)까지 3D로 그리는 것은 무겁다. 권고는 **혼합안: 영웅(과 보스)만 실시간 3D, 일반 적은 지금처럼 구운 그림**.
단, 폰 성능을 실제로 재기 전에는 결정하지 않는다 (3D를 다시 켠 엔진으로 시험 APK가 필요).

## 방식 선택: (b) 인스턴스마다 SubViewport

| 후보 | 장점 | 단점 | 판단 |
|---|---|---|---|
| (a)/(b) 캐릭터마다 SubViewport(256px, 투명, 직교) → 2D 스프라이트 | 지금 2D 구조 그대로 (y 정렬, 이펙트 사이에 끼기, modulate·셰이더·크기·위치 연출). 굽기와 같은 카메라·같은 수묵 셰이더 | 캐릭터마다 그리기 1번 + 렌더 타깃 전환. 9개 = 그리기 호출 19, 30개면 무거움 | **채택** (영웅·보스처럼 몇 개만 그릴 때) |
| (c) 화면 크기 SubViewport 하나에 모두 | 렌더 타깃 1개, 9개에서 GPU 비슷, 메모리 적음 | 모든 캐릭터가 한 장 → 2D 이펙트·소품을 캐릭터 사이에 끼울 수 없음, 수묵 셰이더가 화면 전체(720×1280)에 매 프레임, 2D 카메라 이동·흔들림·확대를 3D 카메라와 맞춰야 함, 캐릭터별 색·깜빡임은 3D 재질로 다시 만들어야 함 | 떼 모드에는 이쪽이 나을 수 있으나 기존 연출 코드를 거의 다 다시 써야 함 |

(b)는 영웅 1 + 보스 1 정도에서 가장 적은 변경으로 동작한다. 적 8마리 이상을 3D로 하려면 (c)를 다시 검토해야 한다 (아래 성능 표).

## 수묵 느낌

같은 셰이더·같은 값(`line_px 1.6, wash 0.25, inner_line 0, grain 0`), 같은 카메라·조명·칸 크기(256px → 0.76배)라 정지 화면 인상은 거의 같다. 차이:
- 구운 그림은 손실 압축(품질 0.58)이라 약간 뭉개지고, 실시간은 더 또렷하다 (눈·무늬가 조금 더 보임).
- 외곽선 굵기 흔들림 잡음이 텍스처 칸 기준이라 모델이 움직이면 먹선 굵기 무늬가 제자리에서 바뀌어 "먹선이 살짝 일렁"인다. 8~16fps 구운 그림에서는 안 보이던 것. 싫으면 흔들림을 끄거나 모델 공간 잡음으로 바꾼다.
- 바깥 먹선을 매 프레임 12번 샘플링 → 스프라이트 하나당 작은 비용 (아래 noink 비교).

| 구운 그림 9 | 1.02 | 0.13 | 3.1 | 2 | 5.8 | 2ms |

읽는 법:
- 구운 그림은 몇 마리든 그리기 호출 2번 (한 장으로 묶임). 3D는 캐릭터마다 호출이 늘고 GPU 시간이 마리 수에 비례한다.
- "최악 500ms"는 3D를 처음 그릴 때 셰이더·버퍼 준비로 생기는 한 번 멈춤으로 보인다 (매번은 아님). 실제 게임에서는 무대 시작 전에 미리 한 번 그려 두는 예열이 필요하다.
- 준비 시간 1.5~1.8초: 추가 동작 파일 4개(.glb, 각 모델+2048 텍스처 포함)를 열어 동작만 꺼내기 때문. 전환하면 동작만 따로 저장(.res)해 수십 ms로 줄일 수 있다.
- 비디오 메모리: 모델 텍스처가 2048×2048 (Meshy 원본). 화면에서 영웅 키가 약 190px이므로 512~1024로 줄여도 차이가 안 보인다 → 1/4~1/16.

안드로이드 저사양 추정 (근거: MX450 대비 Adreno 610·Mali-G52급 GPU는 연산 약 1/10, 타일 GPU라 렌더 타깃 전환마다 타일 저장·불러오기 비용이 붙는다):
- 영웅 1명: GPU 약 3~4ms 추가 → 60fps 예산(16.6ms) 안. 위험 낮음.
- 영웅 + 적 8 (b): 약 18~25ms → 60fps 불가, 30fps 근처. 위험 높음.
- 떼 30마리: 불가능. 구운 그림 유지가 맞다.
- 메모리: 저사양(3~4GB) 기기에서 9개 × 2048 텍스처는 위험, 512 텍스처면 작음.
- 확인 방법: 아래 "시험 APK" 대로 폰에서 Godot 화면 FPS·프로파일러로 재기.

| 다른 영웅 시트 .ctex | 광개토 3.9 / 세종 3.7 / 사임당 3.4 MB |

| 가져온 .scn (메시+동작) | 기본 1.4 MB + 추가 4개 각 1.3 MB (메시 중복) |
| 가져온 텍스처 (2048², 데스크톱 압축) | 파일마다 7.8 MB × 5 (같은 그림 중복) |
| **정리했을 때 영웅 1명 실시간 3D 예상** | 메시 약 1.2 MB + 동작(원본 30fps, 뼈 24개, 클립 9개) 약 0.3 MB + 텍스처 1024² ETC2 약 0.7 MB = **약 2.2 MB** |
| 3D를 다시 켠 엔진 | 지금 커스텀 템플릿은 `disable_3d=yes` (engine-diet). 다시 켜면 엔진 .so가 커진다. 추정 +4~6 MB (빌드해 봐야 정확) |

APK 변화 (추정):
- 혼합안 (영웅 4명만 3D): 시트 -16.3 MB + 3D 자산 +약 9 MB + 엔진 +4~6 MB → **거의 같거나 1~3 MB 줄어듦**.
- 전부 3D (영웅 4 + 적 15 + 보스): 적은 메시를 5~10k 면·텍스처 512로 줄여 약 1 MB씩 → 시트 -28 MB + 3D 약 25 MB + 엔진 +5 MB → 비슷. 용량은 결정 기준이 아니다.
- 구운 칸 수를 늘리는 경우: 칸 수에 비례해 커진다 (순신 동작당 6~8칸 → 16칸이면 시트 약 2배, 영웅 4명 +16 MB).

## 드러나는 문제 (실시간으로 매끄러워지면 보이는 것)

- 확인된 것: 피격 번쩍임·깜빡임, 대시 색·투명, 칼이 닿는 칸은 두 그림이 같은 프레임에 맞는다 (`live3d_combo.png`, `live3d_hit.png`, `live3d_dash.png`).
- 동작 사이 섞기(0.1초) 동안 두 동작의 중간 자세가 지나간다. 이 화면 크기(영웅 키 약 190px)에서는 칼이 몸을 뚫는 장면이 뚜렷하게 보이지 않았지만, 0.5배속 영상(`live3d_compare_slow.mp4`)으로 사용자 눈 확인이 필요하다. 거슬리면 동작별로 섞는 시간을 짧게 한다 (손작업).
- 동작 가져오기 설정이 30fps(`animation/fps=30`)라 60fps에서는 키 사이를 선형으로 이어 그린다. 매끄럽지만 빠른 휘두르기의 날카로움은 원본보다 살짝 무뎌질 수 있다 (가져오기 fps를 60으로 올리면 해결, 용량 소폭 증가).
- 손·얼굴: 256px 칸에서는 손가락이 뭉쳐 보여 구운 그림과 차이를 못 느꼈다. 두루마기 자락은 자동 뼈대라 다리 뼈를 따라 구겨지는데, 끊김 없이 움직이니 그 구김이 계속 보인다 (영상에서 사용자 판단 필요).
- 자유 회전으로 8방향 사이 각도가 보인다. 모델 뒷면은 AI 이미지-3D 특성상 앞보다 덜 다듬어졌을 수 있어, 위로 달릴 때(뒷모습) 확인이 필요하다 (`live3d_run.png`).
- 무기 고정(rigid): 지금은 굽기 직전에 메시의 뼈 가중치를 손뼈 100%로 고친다 (`tools/bake/rigid_weapon.gd`). 실시간도 같은 함수를 모델 불러올 때 쓰면 되지만(시험 코드에 연결됨) 부팅 때마다 계산하므로, 전환하면 (1) 가져오기 단계(EditorScenePostImport)에서 한 번 고쳐 저장하거나 (2) 무기를 몸 메시에서 떼어 `BoneAttachment3D`로 손뼈에 붙인다. (2)가 정석이며 무기 끝 위치도 매 프레임 바로 알 수 있다.
- 3D 모델은 `assets/models/meshy/`(gitignore, 공개 저장소에 올리지 않는 유료 결과물)에 있다. 실시간으로 가면 APK에는 들어가야 하고(내보내기 제외 목록 `assets/models/*` 해제), 저장소에는 여전히 안 올리므로 다른 PC·CI 빌드는 모델 파일을 따로 받아야 한다. 테스트는 모델 없이도 통과하게 만들었다 (모델 없으면 구운 그림으로 돌아감).

## 권고

**혼합: 영웅 4명(+ 보스)만 실시간 3D, 일반 적·떼는 구운 그림 유지.**
- 사용자가 꼽은 "타격 연계·스킬의 흐름"과 "모션의 자연스러움"은 주로 영웅에서 보인다. 영웅만 3D로 해도 섞기·60fps·자유 방향·달리며 공격을 모두 얻는다.
- 영웅 1명은 저사양 폰에서도 예산 안일 가능성이 높다. 적 8마리 이상은 3D 비용이 마리 수에 비례해 위험하다.
- 용량은 거의 같다.
- 먼저 폰에서 확인: 시험 APK (아래)로 FPS를 보고 결정한다. 폰에서 영웅 1명이 60fps를 못 지키면 "지금 방식 유지 + 영웅 칸 수 늘리기 (동작당 12~16칸, +약 16 MB)"로 간다.
